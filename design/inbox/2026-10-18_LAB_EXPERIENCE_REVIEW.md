### 改善すべき点

**A. 働き方の操作と、変わる結果が離れている。** 組み替え390では死亡カードの図・注記・折りたたみを過ぎて初めて就労ボタンに着く。選択後は「上の死亡保障」を見直す必要がある。1280でも縦の分離は同じ。`Lab.tsx:459–506` に操作、`272–275,307–339,378–379` に更新先があり、手動操作は `478` の state 更新のみ。前後比較もない。金額が変わることと、その変化に気づけることは別である。

**B. 「ゼロ」「働けない」の意味が見た目より狭い。** `Lab.tsx:500–502` は、末子独立後の最低就労収入の推定がゼロでも残ると説明する。しかしこれは折りたたみの中。`src/lab/words.ts:179` は「働けない」をゼロへ翻訳する。利用者の「ずっと働けない」を完全に試したと受け取らせかねない。これは注記の量より、操作の意味の問題。決定的な前提として就労操作の直下に出す必要がある。

**C. 病気・けがは「いくら」から「どう考えるか」への橋が薄い。** 全世帯で、開いた短期入院にあるのは主に「長引けば負担は増える」。制度の働きはさらに奥にある（`Lab.tsx:530–561`）。不足390では最初の行は緑でも、その後は青みの灰が続く。違いを読むには前提を開いて自分でつなぐ必要がある。モックの「公的なしくみ／家計への影響／備えのめやす」（`docs/design-mock/lab.html:89–101,173–201`）の説明順は有用。ただしサンプル金額、商品カテゴリ、一律の備え方は転記しない。

**D. 一律の冒頭文が、個別の結果より強く聞こえる。** `Lab.tsx:288–291` の「軽く短いもしもは…貯蓄で受け止め」は原則として理解できるが、貯蓄が少ない世帯にも同じ文が出る。ページの目的は「時期や働き方を変えて、必要額とその理由を確かめます」に絞り、貯蓄で足りるかは各行の**貯蓄の判定**に任せたい。

**E. 単身で「確かめると何が分かるか」が弱い。** 単身390・320では、同額の水平線のために大きな縦空間を使う。`Lab.tsx:315–318` の「お子さんなし」だけでは、なぜ必要額が一定か分からない。算定結果の根拠がある場合だけ「遺す相手の回答がないため、見込むのは葬儀・整理資金です」のような説明を金額の近くに出す。単身という属性だけで不要を断定しない。平らな図も意味はあるが、高さは抑え、本人の病気・休職へ早く進める。

**F. 現行の言葉入力は、質問できるチャットではない。** `src/lab/words.ts:91–112,171–190` は操作3種と unsupported のみ。`Words.tsx:41–42,58–70` は毎回の入力と最新応答を保持し、履歴を送らない。API の AI 文は画面に出ず、許可した値と定型文だけになる（`app/api/lab/words/route.ts:80–88`）。この境界は良い土台だが、説明文を返す新経路には別の検査が必要。現行 API に自由文を足すだけでは足りない。

加えて、既定で畳む入口と、失敗時に入力を畳む処理（`Words.tsx:46–50,77–86`）は、図を押し下げない反面、質問を直す動作を中断する。将来のチャットでは入力保持・同じ位置での再試行を優先する。AI の由来も折りたたみ外に出す。

**G. 色の役割が混ざる。** 病気・けがの大きな金額と「未算定」が CTA と同系の鮮青色。`page.module.css:54` は金額に `--color-primary` を使い、`28` は選択枠にも使う。依頼で指定された「ブランド色は CTA だけ」に合わせ、金額・選択枠・スライダーは墨と中立色へ。判定色は現行のピンク／緑／青みの灰を維持する。図は専用の系列トークンを使い、必要額の帯を不足色で塗らない。

### 死亡保障カードの振る舞い

- 読み出しに「本人の万一」「選択した年齢」「配偶者の就労」をまとめる。現在の診断と試した条件を取り違えさせない。
- 就労ボタンは既存の三択を使う。配偶者なしなら非表示。収入なしなら独立カードをなくし、死亡カードの前提に「配偶者の就労収入は見込んでいません」と短く統合する。ただし独立後の推定が適用される場合はその旨も露出する。
- 就労ゼロの近くに「『ゼロ』でも、お子さんの独立後は就労収入を推定しています。働けない状態が続く場合は必要額が増えることがあります」を表示する。推定を外す計算が未実装なら、「ずっと働けない」を完全に反映したと返さない。部分適用には利用者の選択が必要。
- 「診断時の条件」と「試した条件」を比較できるようにする。まずは直前の一操作だけを対象に、元の必要額・過不足バッジ→変更後を表示し、「元に戻す」を付ける。未変更なら比較欄は出さない。差額が必要なら `src/calc` で作る。判定が変わらないときもその事実を示す。
- 現行の図、保険の点線、緑の塗り、年齢表、読み上げ用テキストを活かす。前後比較のために図を二枚積まない。単身の平らな図は根拠文を添え、低くする。
- 「現在の死亡保障で減らせる箇所は…」は現在の年齢の説明として残す（現行 `Lab.tsx:593–597` は `scenario.now`）。選択した未来年齢のバッジと違う場合にも、対象時点を明示する。

### 病気・けがの行

金額・貯蓄の判定を閉じた見出しに残す。開いた先は「使う公的な支え」「家計への影響」「備えのめやす」を短く説明する。たとえば「働けない間の収入減と自己負担を見ています。いまの前提で貯蓄と比べた結果は、上の貯蓄の判定です」。制度の適用有無はエンジンの根拠に合わせる。家計への影響を新しい金額で語るなら、先に算定出力を用意する。

各行は同じ貯蓄を使う単独試算で、足し合わせないことを一覧直下に一度だけ明示する。障害の未算定には、金額の代わりに「何の確認が必要か」を置く。病名から医療費や復帰時期を推測しない。モックの説明の型を使い、商品カテゴリの助言は採らない。

### 質問パネル

見出しは **「この結果について聞く」**。折りたたみの外に「ことばは AI が書きます。数字と判定は計算エンジンのもので、AI は変えられません」を置く。実装・検査が完了するまでは現行の「言葉で確かめる」を維持し、新しい質問チップを公開しない。

入口には、利用できる対象だけ候補を出す。死亡保障なら「この過不足の理由」「遺族年金って何？」と、対応する条件変更候補。単身には配偶者の候補を出さず、配偶者収入なしの世帯にも働き方変更を勧めない。現行 `Words.tsx:80` の hasSpouse だけでは足りないため、操作可能性も条件に使う。チップは入力を埋めるだけで、AI送信や条件変更は勝手にしない。

現行の一往復・履歴なしを初期拡張でも維持する。対象名と「毎回、この画面の条件で答えます。前のやり取りは引き継ぎません」を入力近くに表示する。「それは？」のように対象が取れない質問には選び直しを求める。会話を覚えている演出はしない。短い応答で足りる結果質問を先に成立させ、会話履歴は別の任意拡張とする。

質問と条件変更は送信後に区別する。説明だけなら現在の状態を変えない。変更要求なら「こう受け取りました」→計算済みの前後プレビュー→「この条件を試す」で反映する。これは保存の承認ではなく、言葉の解釈を利用者が確かめる操作。複合質問で一部しか扱えないときも、黙って一部を適用しない。

応答は原則、答えの一文・根拠・確認先の短いまとまり。自由文を伸ばしてページ長を稼がず、既存の図や前提を参照する。失敗時は入力を保持し、欄を勝手に閉じず、再試行とボタン操作への戻り道を示す。算定値はそのまま保つ。読み上げは応答と変更の要点だけを通知し、全カードを繰り返さない。送信中の二重送信を防ぎ、古い条件への応答は現在の結果に混ぜない。

## 3. チャットが答えてよい範囲と線引き

ここにある文は**実装提案の例文**であり、個別の金融・医療判断ではない。制度の説明は採用済みの出典に沿って作り、公開時に内容・有効期間を確認する。`{{...}}` は表示例の記号で、既存 API にその名前のフィールドがあることを意味しない。数値・単位を含む整形済み文字列はエンジン出力から差し込み、判定は enum と既存バッジから描画する。

| 質問・意図 | 答えてよい内容と例文 | 境界・次の行動 |
|---|---|---|
| 「なぜ不足？」 | 「いまの前提では、必要保障額の幅に対して現在の保障が下回っています。必要保障額は {{necessaryRange}}、現在の保障は {{coverageAmount}} です。」＋過不足の判定バッジ | 不足が確認できる対象だけに出す。世帯の不足と本人死亡を混同しない。内訳の根拠がなければ「教育費が原因」と推測せず、算定済み内訳へ案内 |
| 「遺族年金って何？」 | 「亡くなった方に支えられていた家族への公的な年金です。この試算で見込んだ内容は『死亡算定の前提』で確認できます。」＋確認済みの公的出典 | 制度の概要とこの試算への反映は答える。個人の受給資格・支給決定は確約せず、加入記録などを公的窓口で確認する案内へ |
| 「年齢を変えたら？」 | 「万一の年齢を {{selectedAge}} にして比べます。必要保障額は {{beforeRange}} から {{afterRange}} になります。」＋同じ軸の前後バッジ | 対応範囲の年齢だけ。AIは前後の差を計算しない。将来の貯蓄・返済・制度まで予測したとは言わない |
| 「配偶者がずっと働けなかったら？」 | 「この画面の『ゼロ』には、お子さんの独立後の就労収入の推定が残ります。働けない状態が続く場合の必要額は、この条件では確かめきれません。」 | 完全対応と偽らない。現行のゼロ条件で試すかは利用者に選んでもらい、長期に働けない前提は精査事項に残す |
| 「なぜ年齢を変えても同じ？」 | 根拠があるときだけ「この試算では、遺族の生活費を見込まず、葬儀・整理資金を見ています。そのため、この範囲では必要額が変わりません。」 | 横ばいの原因を AI が推理しない。対象となる算定理由が返らない場合は前提を示すところまで |
| 「休職の金額は全部足す？」 | 「各行は別々に起きた場合の負担です。同じ貯蓄と比べているので、足し合わせません。死亡保障の必要額とは、資産を差し引く前か後かも異なります。」 | 同時発生や連続休職への安全性は保証しない。複合ケースは未算定と明示 |
| 「障害で働けなくなったら、いくら？」 | 「長期の収入減を含む金額は未算定です。障害年金の受給条件などを確認する必要があります。概算の数字で穴埋めはしません。」 | 未算定をゼロや不足バッジに変えない。確認対象を示し、公的窓口・資料へ。病状や復職の判断は扱わない |

「精査が要る」は、何でも断る語にしない。**説明できるところ→分からない条件→確認する資料・場所**の順で返す。たとえば配偶者の扱いは現行 `Lab.tsx:448–449` の「妻として計算」の前提があるため、その前提と異なる質問に同じ受給見込みを断言しない。対象外世帯は既存 `page.tsx:52–62` と同様、金額を作らない。

### 答えを安全に成立させる仕組み（チャット公開の必須条件）

1. **意図を分ける。** 操作3種の構造化出力を残し、結果説明・用語説明・非対応を別の経路にする。説明の自由文を操作として実行しない。AIに保存・送信・削除などのツール権限を渡さない。
2. **現在の対象を固定する。** 本人／選択年齢／就労／シナリオ／判定軸／基準日／版を対象スナップショットとして持つ。現 API は元の回答 query と text のみ（`Words.tsx:61`）で、選択中の年齢・就労を送らない。結果質問の追加には、この差を埋める必要がある。信頼する算定値はサーバ側で求め、クライアントが送る金額を正本にしない。
3. **根拠を用意する。** `src/calc/lab.ts:50–63` の `LabPoint` にはレンジ・過不足の判定・前提はあるが、原因別の寄与額を直接返していない。「不足の最大原因」「何を変えれば解消するか」を説明するには算定側の根拠が要る。未提供の理由を AI に補わせない。用語は出典つきの管理済み説明を使い、回答に出典を添える。
4. **数値・判定を文章から分離する。** AIは金額、割合、年齢、期間などの数値を書かず、許可リストのプレースホルダだけ使う。判定文も enum に連動する定型表示にする。無効・欠落したプレースホルダ、禁止名称、商品カテゴリ、煽り、根拠にない断定は破棄して定型の案内に戻す。検査前の文章をストリーミングで一瞬でも見せない。
5. **必要な情報だけ渡す。** 自由入力をURL・分析・アプリログ・永続履歴に残さない。外部AIへの処理上の送信は入力前に説明し、氏名や証券番号を求めない。「保存なし」を「外部へ送られない」と言い換えない。既存 API のログ抑制（`route.ts:89–100`）を維持する。
6. **回答期限を設ける。** 応答待ちに条件が変わったら、古い対象の説明を現在の結果として表示しない。通信失敗・検査失敗・非対応を区別し、どれも算定結果や入力値を壊さない。
